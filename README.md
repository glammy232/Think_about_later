# Круг

**Круг** — веб-приложение для совместного учёта финансов внутри квартиры, семьи или компании друзей. Участники создают общую группу, фиксируют расходы, доходы и прямые долги, а система автоматически рассчитывает личные балансы, показывает, кто кому должен, и предлагает минимальный набор переводов для закрытия задолженностей.

Проект объединяет в одном интерфейсе повседневный учёт операций, аналитику, историю долгов, уведомления, распознавание QR-кодов кассовых чеков и финансового AI-помощника.

## Задача проекта

При совместном проживании или регулярных общих покупках финансовая информация обычно оказывается разбросана между сообщениями, заметками и таблицами. Из-за этого сложно быстро ответить на вопросы:

- кто и сколько заплатил;
- как разделить конкретный расход;
- кто кому должен;
- какие долги уже погашены;
- на какие категории уходит больше всего денег;
- каким будет расход к концу месяца при текущем темпе.

«Круг» хранит все операции группы в едином месте и выполняет расчёты на сервере, поэтому каждый участник видит согласованное состояние общих финансов.

- добавление расходов и доходов;
- фильтрация операций по типу и категории;
- удаление операций;
- стандартные и пользовательские категории;
- указание плательщика, участников, даты и источника операции;
- три способа разделения расхода: поровну, вручную по суммам и по процентам.

- распределение оплат между участниками;
- фильтрация аналитики за период от 1 до 12 месяцев;
- прогноз расходов до конца текущего месяца;
- сравнение периодов и моделирование изменения расходов через AI-инструменты.

- уведомления о долгах, погашении задолженности и темпе расходов;

## Финансовая модель

### Распределение расхода

Для каждого расхода указываются плательщик, общая сумма и участники, между которыми делится операция.

При равном распределении сумма переводится в копейки, делится на количество участников, а остаток распределяется по одной копейке. Поэтому сумма долей всегда точно совпадает с суммой операции.

Пример: расход 1 000 ₽ на трёх участников будет разделён как 333,34 ₽, 333,33 ₽ и 333,33 ₽.

При ручном распределении backend проверяет, что:

- все участники указаны ровно один раз;
- для каждого участника задана сумма;
- сумма всех долей совпадает с общей суммой расхода с точностью до копейки.

При процентном распределении:

- для каждого участника задаётся процент;
- сумма процентов должна составлять 100%;
- последняя доля получает остаток округления, чтобы итог точно совпадал с суммой операции.

### Расчёт чистых балансов

Для каждого участника создаётся баланс, изначально равный нулю. Затем backend последовательно учитывает:

1. Общие расходы: сумма добавляется плательщику, после чего из балансов участников вычитаются их доли.
2. Активные прямые долги: сумма вычитается у должника и добавляется кредитору.
3. Выполненные платежи: сумма возвращается в баланс отправителя и вычитается у получателя, закрывая соответствующую задолженность.

Интерпретация результата:

- баланс больше нуля — участнику должны деньги;
- баланс меньше нуля — участник должен деньги;
- нулевой баланс — расчёты закрыты.

### Рекомендуемые переводы

После расчёта чистых балансов система формирует списки должников и кредиторов. На каждом шаге крупнейший текущий долг сопоставляется с крупнейшей суммой к получению. В перевод попадает минимальная из этих двух сумм, после чего остатки пересчитываются.

Так исходный набор операций преобразуется в компактный список переводов без изменения итогового баланса участников.

## Модели и валидация

Pydantic-модели отклоняют некорректные данные до выполнения бизнес-логики.

Основные правила:

- сумма операции и долга должна быть больше нуля;
- имя, название группы, категория и описание не могут состоять только из пробелов;
- длина текстовых полей ограничена;
- участники операции не могут повторяться;
- плательщик и участники должны состоять в текущей группе;
- ручные доли должны совпадать с участниками и общей суммой;
- проценты должны составлять 100%;
- платёж не может превышать активный рассчитанный долг;
- файл чека должен быть изображением размером не более 10 МБ.

Типы операций: `expense` и `income`. Способы распределения: `equal`, `custom` и `percentage`. Статусы долга: `active` и `settled`.

## Идентификация пользователя

Текущий demo-контракт передаёт идентификатор пользователя в заголовке `X-User-Id`. Frontend сохраняет `krug_group_id` и `krug_user_id` в `localStorage` и добавляет заголовок к пользовательским запросам.

Это облегчённая идентификация для демонстрационной версии, а не полноценная система аутентификации. Для production необходимо добавить регистрацию, безопасные сессии или JWT, проверку членства и ролевую модель на всех изменяющих маршрутах.

## Хранилище и PostgreSQL

Приложение работает через интерфейс `Storage`. Бизнес-логика вызывает единый контракт, не зная, где физически расположены данные.

- Если задан `DATABASE_URL`, создаётся `PostgresStorage` с пулом от 1 до 10 соединений.
- Если `DATABASE_URL` отсутствует, используется пустой `InMemoryStorage`.

PostgreSQL-реализация поддерживает Supabase и его transaction pooler. Идентификаторы из API приводятся к числовым идентификаторам базы, а prepared statements отключены для совместимости с повторным использованием pooler-соединений.

SQL-миграции расположены в `supabase/migrations` и создают таблицы пользователей, групп, участников, категорий, расходов, долей, доходов, прямых долгов и погашений, а также необходимые индексы и ограничения.

### Подключение Supabase/PostgreSQL

1. Примените миграции через Supabase SQL Editor, Supabase CLI или другой клиент PostgreSQL.
2. Создайте `.env` на основе `.env.example`.
3. Добавьте строку подключения:

```dotenv
DATABASE_URL=postgresql://USER:PASSWORD@HOST:PORT/DATABASE
```

Для сервера без маршрута IPv6 рекомендуется использовать IPv4-совместимый Supabase pooler, если он доступен для проекта.

Секреты и настоящие строки подключения нельзя добавлять в Git. Файл `.env` исключён через `.gitignore`.

## AI-помощник

Помощник использует DeepSeek через OpenAI-compatible API. Системный prompt дополняется актуальным контекстом: текущей датой, пользователем, группой, списком участников, доступными категориями и валютой.

AI не обращается к базе напрямую. Он выбирает функцию из `ai/tools.json`, backend проверяет аргументы, выполняет операцию через сервисы и Storage, после чего возвращает структурированный результат модели.

Доступные группы инструментов:

- сводка расходов и доходов;
- расходы по категории и крупнейшие категории;
- сравнение периодов;
- статус и прогноз бюджета;
- распределение оплат;
- текущие балансы и рекомендуемые переводы;
- моделирование изменения трат;
- поиск мероприятий через публичный API KudaGo;
- создание расхода, дохода или прямого долга после серверной валидации.

Один запрос ограничен восемью последовательными циклами tool calling. История диалога сохраняется по `conversation_id`, в модель передаются последние 30 сообщений.

Для прогноза бюджета за текущий месяц требуется минимум семь дней данных. Если данных недостаточно, backend возвращает специальный статус вместо необоснованного прогноза.

## Уведомления

Система создаёт уведомления:

- о текущем непогашенном долге;
- о прогнозе расходов после накопления минимум семи дней данных;
- о погашении долга — отдельно должнику и получателю;
- вручную через тестовый endpoint.

Повторные долговые и бюджетные уведомления ограничиваются интервалом в одни сутки.

В текущей реализации уведомления хранятся в памяти процесса. После перезапуска контейнера история уведомлений очищается. Для production их следует перенести в PostgreSQL и добавить endpoint отметки о прочтении.

## Работа с чеками

`POST /api/receipts/parse` принимает исходную строку российского фискального QR-кода и извлекает сумму, дату и служебные поля без обращения к ФНС или ОФД.

`POST /api/receipts/scan` принимает изображение и пытается найти QR-код через OpenCV. Поддерживается предварительная нормализация распространённых форматов, включая HEIC/HEIF. Результат возвращается как черновик расхода, который пользователь может проверить перед сохранением.

## Быстрый локальный запуск

### Требования

- Python 3.12;
- `pip`;
- PostgreSQL — необязательно для локального in-memory режима;
- Docker — необязательно.

### Запуск через Python

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
uvicorn app.main:app --reload
```

После запуска доступны:

- приложение: <http://localhost:8000/demo>;
- frontend: <http://localhost:8000/app/onboarding.html>;
- Swagger UI: <http://localhost:8000/docs>;
- OpenAPI JSON: <http://localhost:8000/openapi.json>;
- health check: <http://localhost:8000/api/health>.

Без `DATABASE_URL` приложение запускается с пустым временным хранилищем. Созданные данные будут потеряны после остановки процесса.

### Запуск через Docker Compose

```bash
cp .env.example .env
docker compose up --build -d
docker compose logs -f api
```

Остановка:

```bash
docker compose down
```

## Переменные окружения

| Переменная | Обязательность | Назначение | Значение по умолчанию |
|---|---|---|---|
| `DATABASE_URL` | для постоянного хранения | PostgreSQL/Supabase connection string | in-memory режим |
| `FRONTEND_ORIGINS` | нет | разрешённые CORS origins через запятую | localhost:3000 и localhost:5173 |
| `DEEPSEEK_API_KEY` | для AI | API-ключ DeepSeek | пусто |
| `DEEPSEEK_BASE_URL` | нет | OpenAI-compatible endpoint | `https://api.deepseek.com` |
| `DEEPSEEK_MODEL` | нет | модель помощника | `deepseek-chat` |
| `APP_TIMEZONE` | нет | часовой пояс приложения | `Asia/Yekaterinburg` |

Проверить активный режим:

```bash
curl http://localhost:8000/api/health
```

Пример ответа:

```json
{
  "status": "ok",
  "storage": "PostgresStorage",
  "ai": "configured"
}
```

## Docker и CI/CD

`Dockerfile` использует multi-stage сборку на базе Python 3.12. В финальный образ копируются runtime, backend, AI-конфигурация и статический frontend.

Контейнер запускает один Uvicorn worker. Это сохраняет согласованность временного in-memory режима. При постоянном PostgreSQL-хранилище конфигурацию можно расширить несколькими процессами, но состояние диалогов AI и уведомлений также потребуется вынести из памяти.

Workflow `.github/workflows/deploy.yml` собирает образ, публикует его в GitHub Container Registry, подключается к серверу по SSH и пересоздаёт Docker-контейнер.

Для workflow требуются GitHub Secrets:

```text
SERVER_HOST
SERVER_USER
SSH_PRIVATE_KEY
```

Файл `/opt/project/.env` с `DATABASE_URL` и API-ключами должен быть создан непосредственно на сервере и не должен храниться в репозитории.

## Ограничения текущей версии

- `X-User-Id` является demo-идентификацией и не заменяет аутентификацию;
- уведомления и история AI-диалогов хранятся в памяти процесса;
- in-memory режим предназначен только для локальной разработки;
- валюта пользовательского интерфейса сейчас зафиксирована как RUB;
- поиск мероприятий зависит от доступности внешнего API KudaGo;
- сканирование чека извлекает данные из QR-кода и не запрашивает официальные данные ФНС/ОФД;
- для production необходимы HTTPS, полноценная авторизация, централизованные логи, резервное копирование и мониторинг.

## Безопасность

- не публикуйте `.env`, API-ключи и пароли базы данных;
- при утечке секрета немедленно замените его;
- используйте HTTPS на публичном сервере;
- выдавайте базе данных минимально необходимые права;
- не используйте demo-заголовок `X-User-Id` как production-аутентификацию;
- проверяйте миграции и создавайте резервную копию перед изменением production-базы.
